# 禅道 Bug 人员查询分页修复设计

## 1. 背景与问题

`query_user_bugs` 和带 `assigned_to` 条件的 `search_bugs` 会在部分人员名下错误返回 0 个 Bug。单个 Bug 详情仍能正确显示状态和指派人。例如 Bug 2769、3221、3346 的详情都显示状态为 `active`、指派账号为 `xujiangshan`，但按徐江珊或账号 `xujiangshan` 查询时结果为空。

问题可以稳定复现，且与姓名解析无关：姓名和账号都会被正确解析为 `xujiangshan`，错误发生在后续 Bug 列表读取阶段。

## 2. 根因

禅道 21.7.8 的产品 Bug 列表端点使用 `pageID` 表示页码。当前 `BugService._read_scope` 发送的是 `page`。

服务端忽略 `page` 后始终返回第一页，并在响应 `pager.pageID` 中持续报告 1。插件却依据本地循环变量继续递增页码，因此会重复读取第一页、按 ID 去重，并最终把不在第一页的 Bug 漏掉。

当筛选状态为 `active` 时，插件使用 `browseType=all` 获取完整列表再本地过滤。目标 Bug 不在全部 Bug 的第一页，所以人员查询返回空；`get_bug` 不分页，因此能返回正确详情。

## 3. 方案选择

采用最小根因修复：只将 Bug 范围列表请求的页码参数从 `page` 改为 `pageID`。

不同时发送两个页码参数，因为重复参数会掩盖服务端约定并增加兼容性歧义。不在本次改动中重构产品列表、用户列表或分页抽象，因为没有证据表明它们导致当前故障。

## 4. 代码变更

修改 `src/zentao_ai/bugs.py` 中 `BugService._read_scope` 的请求参数：

- 保留 `browseType`；
- 保留 `recPerPage`；
- 将 `page` 替换为 `pageID`；
- 不改变现有去重、过滤、排序、汇总、最大结果数或截断标记逻辑。

`query_my_bugs`、`query_user_bugs`、`query_team_bugs` 和 `search_bugs` 都复用 `_read_scope`，因此修复会覆盖所有 Bug 列表查询入口。

## 5. 测试设计

使用测试驱动方式新增回归场景：

1. 模拟端点只有在收到 `pageID=2` 时才返回第二页；若收到旧参数 `page`，则继续返回第一页。
2. 第一页包含其他人员的 Bug，第二页包含指派给目标账号的激活 Bug。
3. 调用人员查询并断言第二页目标 Bug 被返回。
4. 断言实际请求页码依次为 1、2，且请求参数使用 `pageID`、不再使用 `page`。

修复前测试应因第二页未被读取或缺少 `pageID` 而失败；修复后测试应通过。随后运行完整 `pytest`、Ruff 和 mypy，确认没有回归。

## 6. 本机更新与验收

自动化验证通过后，从修改后的本地仓库重新安装 `zentao-ai-assistant` 到现有 pipx 环境。插件 Marketplace 与 Skill 没有行为或合同变化，不修改 Marketplace 条目。

验收包括：

- 直接使用修复后的服务按 `xujiangshan` 查询激活 Bug；
- 确认结果至少包含 2769、3221、3346；
- 确认三条记录的状态均为 `active`、指派账号均为 `xujiangshan`；
- 运行 `zentao-ai doctor`，确认配置、登录、API 与 MCP 能力未受影响；
- 提示新建 Codex 任务，使新的 MCP 进程加载已更新的本地命令。

## 7. 安全与边界

本次修复只改变只读查询的分页参数，不写入或修改任何禅道 Bug。测试和日志不得记录密码、Token、Cookie、认证头或完整真实业务响应。

## 8. 完成标准

- 回归测试在旧实现上失败，在修复后通过；
- 完整测试、格式检查和类型检查通过；
- 本机安装包来自修改后的仓库；
- 实际人员查询能返回徐江珊的 2769、3221、3346；
- 单个 Bug 详情、其他筛选和 MCP 工具合同保持不变。
